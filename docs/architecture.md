# 架构总览

## 仓库结构

采用 **"核心库 + 实例工程"** 双层结构，核心库与具体硬件平台解耦，实例工程填充板级实现。

```
<project-root>/
├── core/                          ← 平台无关可复用库（骨架）
│   ├── include/
│   │   ├── LS_Config/             ← 配置宏、类型定义、数据表（无实例）
│   │   ├── L1_Orchestration/      ← 启动流程、主循环编排、核心数据结构
│   │   ├── L2_Core/               ← 业务算法、协议处理、运行时工具
│   │   │   ├── Business/          ← 业务逻辑模块
│   │   │   ├── Protocol/          ← 通信协议处理
│   │   │   └── Runtime/           ← 调度器、队列、调试工具
│   │   └── L3_Hal/                ← 硬件抽象层 API
│   └── src/                       ←（同 include/ 层级结构）
├── examples/<instance>/           ← 板级工程与驱动实现
│   ├── software/
│   │   ├── Application/           ← 实例应用层（main、平台适配）
│   │   ├── Utilities/             ← 外设驱动实现（L4 BSP层）
│   │   ├── Firmware/              ← 芯片 SDK
│   │   ├── RTE/                   ← Keil 运行时环境
│   │   └── list/                  ← 编译列表输出
│   ├── hardware/                  ← 管脚定义等硬件文档
│   ├── build/                     ← 构建输出目录
│   ├── Project.uvprojx/optx      ← Keil 工程文件
│   └── RTE_Components.h           ← Keil 组件配置
├── docs/                          ← 所有文档收敛于此
│   ├── architecture.md            ← 唯一结构说明书（SSOT）
│   ├── development.md             ← 开发流程
│   └── ...
├── dev-guidelines/                ← 开发指南与规则
└── .github/                       ← 工作流治理（可选）
```

## 分层架构模型

运行时依赖方向严格单向：**L1 → L2 → L3 → L4**（层号从下至上递增，上层依赖下层）。
LS 层不属于运行时依赖链——它是纯编译期实体，可被任何层通过 `#include` 引用。

```
┌──────────────┐
│  L1 编排层    │  ← 持有所有运行时实例（单例或聚合结构体）
├──────────────┤
│  L2 核心业务层 │  ← 业务算法、协议处理，不持实例，通过指针操作
├──────────────┤
│  L3 HAL 层    │  ← 平台抽象 API、数学变换、传感器接口（纯函数）
├──────────────┤
│  L4 BSP 层    │  ← 外设驱动、芯片库实现（在实例工程的 Utilities/ 中）
└──────────────┘

            ┌──────────────┐
            │  LS 配置层    │  ← 纯编译期实体，不参与运行时调用链
            │               │    可被任何层 #include
            │               │    无函数/变量/实例
            └──────────────┘
```

### 各层职责

| 层级 | 职责 | 实例化职责 |
|------|------|-----------|
| **LS (配置层)** | 符号定义、功能开关宏、默认值、编译期约束检查、类型定义、静态数据表 | 无实例（纯宏与类型） |
| **L1 (编排层)** | 启动流程、主循环编排、持有所有核心数据结构实例 | **持有所有运行时实例**（系统结构体、队列缓冲区、调度器状态等） |
| **L2 (核心业务层)** | 业务算法、协议帧处理、运行时工具（调度器、队列、调试生成） | 不持实例，通过指针操作传入的数据结构 |
| **L3 (HAL 层)** | 平台抽象 API、数学变换、查表、传感器采样、执行器输出 | 无实例（纯函数，或操作传入结构体的字段） |
| **L4 (BSP 层)** | 外设驱动初始化、中断处理、芯片库封装 | 芯片固有实例（外设寄存器、全局句柄） |

### 分层调用关系

```
L1 包含 LS 头文件获取宏与类型，持有运行时实例
   ↓
L1 调用 L2 各模块的函数，传入实例指针
   ↓
L2 调用 L3 平台 API 完成硬件交互（L2 也可引用 LS 宏与类型）
   ↓
L3 调用 L4 提供的驱动接口（L3 也可引用 LS 宏与类型）

LS ───────→ 可被 L1/L2/L3/L4 任意一层 #include，纯编译期无运行时开销
```

## 当前实例

当前项目包含一个实例工程 `examples/GD32F303_DevBoard/`，详情见该实例目录下的文档。

当前核心库包含 L1 `BoostControl_*`、L2 `IncrementalPI_*` 以及 L3 `ADCMeasurement_*`、`DutyControl_*`、`ControlTimer_*`。L1 持有电压环和电流环实例、累加 L2 返回的单周期增量并编排 10 kHz 控制顺序；L2 只根据当前误差和历史误差计算已限幅增量；L3 分别抽象 ADC 实际值、三相占空比和控制时基，不向公共头文件暴露芯片厂商 SDK 类型。实例工程 L4 使用 TIMER4 提供 10 kHz 中断，中断入口只清除更新标志并调用已注册的控制回调；Application 层使用 `AppBoostMonitor_*` 连接 L1 状态读取与 L4 USART0 调试输出，避免平台相关打印逻辑进入核心 L1。

## 架构约束

以下约束是保持依赖清晰、避免耦合混乱的关键规则：

### 反向包含禁止
- **L2 任何模块不得包含 L1 的头文件**。L2 不应感知编排层的存在。
- 公共头文件不得暴露芯片厂商 SDK 头文件（如 `stm32f1xx_*.h`、`gd32f30x_*.h`）。LS 不受此限制——任何层都可包含 LS。

### 实例所有权集中
- **L2 层不得持有任何实例**（全局变量、静态缓冲区等）。所有实例由 L1 在系统结构体中分配。
- L2 通过函数传入的指针操作实例数据，不自行分配或持有。
- L1 是唯一编排者，实例化所有核心数据结构（系统上下文、队列、通道等），在初始化时传递给 L2 各模块。

### 配置收敛
- 所有可配置参数、默认值、功能开关必须收敛在 LS 层的配置头文件中。
- 禁止在业务 `.c` 文件中散落默认值或魔法数字。
- 配置宏文件之间不交叉依赖（不互相 `#include`），由统一入口头文件按序包含。

### 硬件访问规范化
- L2 访问硬件必须通过 L3 提供的平台抽象 API，不得直接调用 L4 驱动。
- L4 不得反向依赖核心库的业务逻辑源码。

### 宏裁剪链路一致性
- 功能裁剪宏控制某特性时，该宏必须同时保护声明、定义、调用三个环节。
- 功能宏关闭后，必须同步收口所有引用点，避免"裁掉定义但未裁掉调用"式链接错误。

### 跨模块调用限制
- L2 内部各子模块（如业务算法 / 协议 / 运行时）不直接跨模块调用。
- 数据通过 L1 统一协调传递，不形成模块间的隐式依赖链。

## 扩展指南

- 添加新的实例工程：复制现有 `examples/<instance>` 并修改硬件参数
- 添加核心库代码：在 `core/` 对应层目录中添加 `.h` 和 `.c` 文件
- 添加新外设驱动：在实例的 `Utilities/` 下新建模块目录
